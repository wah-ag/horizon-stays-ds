# Build a component

## When to use this
Use this when you are turning one Figma component into one coded component in
`src/components/`, or fixing one after a QA report. Do not use it for building a
whole screen, or for anything that spans more than one node.

## An unbound property is a design gap
A property the design leaves unbound — a loose hex, a stray px, a font set by hand —
is a **design gap to report, not a decision to make**. Report it, name the node and
the property, and build the rest. Never fill it with the nearest token, a core
primitive or a raw value: a guess shipped as code looks exactly like a decision the
designer made, and nobody goes back to check.

## Steps
Four stages build the component; the fifth hands it over. **Every stage ends with a
check, and the check must be green before the next stage starts.** Never leave a
stage red: fix it and re-run, or stop and ask. A later stage never starts on an
earlier stage's failure.

### 1 · Schema — read the design
Pull the node through the Figma connection. Write down the **variant matrix**:
every variant property, every size, every state in the component set. That list
drives the props, the stories, and the QA pass.

**Check:** the matrix lists every variant × size × state in the Figma component set,
with none dropped, and every property in the design has a prop or a token binding
written down. Nothing is "I'll work it out when I write it."

### 2 · Tokens — resolve, don't choose
For each visual property, find the semantic token that carries that meaning in
the build output under `config/css/`. Never a raw value. Never a core primitive
directly — the colour ramps, spacing and sizing in `config/css/core.css`
(`--color-blue-500`, `--color-grey-800`) are the base layer, and a component that
reaches for one has skipped the semantic token that should sit in front of it,
such as `--color-text-brand`.

`config/` is generated by `npm run build:tokens`. Read it, never edit it. The
component consumes a platform entry point — `config/css/index.css`,
`index-mobile.css` or `index-back-office.css` — never an individual token file.

A property the design leaves unbound is a design gap. Report it and build the rest.
Never substitute the nearest token, a core primitive or a raw value for it.

**Check:** every value resolves to a semantic token, and the unbound ones are raised
rather than substituted.

### 3 · Implement — structure and behaviour
Create `src/components/<Name>/<Name>.js` and `<Name>.css`. Prop names match the
Figma property names exactly. Every CSS value uses `var(--token-name)`.

Layout is translated, not eyeballed: auto-layout becomes flex or grid carrying its
direction and alignment, gap and padding come from their spacing tokens.

Interactions actually work. Default, hovered, pressed, focused, disabled,
destructive — whichever the component uses — as behaviour, not just a class that
changes colour.

**Check:** no raw hex, px or font value in `<Name>.js` or `<Name>.css` — every
visual value is a `var(--token)` — and every state in the matrix is wired to real
behaviour: disabled cannot be clicked, focused comes from `:focus-visible`, hovered
and pressed from the pointer.

### 4 · Check — render it and compare
Write `<Name>.stories.js`, one story per row of your matrix. **Record the Figma
node URL at the top of that file** — QA tests against the node, not against your
story file, and cannot start without it.

Then run
`npm run storybook` and **look at it**: the sidebar lists your stories, the canvas
draws them, the console is clean, every state clicks through.

Then compare each story against the Figma node: spacing, colour, size, radius, states.

**Check:** `npm run build-storybook` completes, and every matrix row matches its
node, or the difference is reported.

This stage is your **self-check**, and local Storybook is the right place for it.
It is not the handoff, and it is not QA. Do not hand anything to QA from here.

### 5 · Deploy — staging, then the registry, in that order
Only once stage 4 is fully green. Never before, and never partly.

1. **Security check, build mode.** With everything committed, run
   `npm run build-storybook`, then `node scripts/security-check.mjs build`. It must
   exit `0`. On a failure, follow `.claude/skills/security-check/SKILL.md` and stop.
2. Merge the component branch into `staging` by PR. Never into `main`.
3. Deploy that staging build to Vercel.
4. **Open the deployed URL yourself and see the component render.** A link to a
   build you have not looked at is a lie in a cell.
5. **Security check, live mode.** Run
   `node scripts/security-check.mjs live --url <staging URL> --expect public`. It
   must exit `0`. QA and the PM open this link without logging in, so staging is
   meant to be public.
6. Write that URL into the registry's `Staging Storybook` column, plus `Commit`,
   a `GitHub Commits` row, and `Composes` if this component imports another.

On a first build, writing `Staging Storybook` flips `Development` to
`Ready for Testing`, which is what wakes QA. **That cell is the entire handoff** —
QA starts from the link in the registry, in Claude in Chrome, and tests that
deployed build and nothing else. QA refuses when the cell is empty, so a component you did not deploy is a
component nobody tests.

**Check:** both security checks exited `0`, and the staging URL is deployed, opened,
seen to render, and written to `Staging Storybook`.

- [ ] `npm run build-storybook` completes

- [ ] Every state in the matrix has real behaviour, not only a class that changes colour
